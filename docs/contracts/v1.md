命名空间为 `Shixu::Contracts::V1`。接口类是纯虚声明，没有默认成功实现，不会修改数据库。
各成员用自己的实现类或薄适配器实现接口，复用现有业务类和存储；不需要整体重写。
`IInventoryService` 适配现有唯一 InventoryManager；不创建第二个库存连接。

C 的接口和模型不依赖 Qt；D 接口因复用已有 Qt 卡片而单独放置。Qt 与 std::string 在适配边界按 UTF-8 转换。
服务返回值为值语义，不跨模块传数据库指针或 QObject 所有权。业务错误通过结果返回。
所有持久化调用由单一协调服务串行执行；重复调用保护仍须持久化，不能依赖按钮禁用。

## 统一基础规则

| 项目 | 确定约定 |
|---|---|
| 食材匹配 | A 的标准名称，C 同步名称；同名需求先合并，不另发明 foodId |
| 批次 ID | B 数据库稳定正数 `int64_t`，不能是列表下标 |
| 菜谱 ID | 现有正数 `int`；找不到返回 Failed/NotFound |
| 份数 | 本版只接受 1；其他值 InvalidArgument，预留字段供未来扩展 |
| 计算重量 | 克；所有数量/重量要求有限数值，拒绝 NaN/Inf/负数 |
| 日期 | YYYY-MM-DD；仅到期日允许空字符串表示未知 |
| 完成时间 | YYYY-MM-DD HH:mm:ss，应用时区 Asia/Shanghai，重试不重新取今天 |
| 临期 | 完成事件当天到未来 3 天，含两端；过期是到期日严格早于当天 |
| 事件编号 | 集成层生成小写、无花括号 UUID；每次实际做饭一次，重试沿用 |
| 浮点误差 | 计算不按 UI 小数位舍入；比较容差 1e-6 g，仅容差内尾差可归零 |

`OperationResult`：Succeeded=本次成功；AlreadyApplied=同一事件已保存；NeedsConfirmation=未执行，需重新确认；Failed=失败。
成功/已处理的 errorCode 为 None，失败/需确认必须提供对应错误码和中文 message。
查询只返回 Succeeded 或 Failed；Succeeded + 空列表表示确实无数据，不能把读取失败伪装为空库存。
NotFound 用于不存在的菜谱/事件；InvalidData 用于已损坏的存储内容；EventConflict 表示同 ID 不同内容。
幂等返回携带原始保存结果，界面不能再次把 pointsAdded 加到自己的累计值。

## A/B：沿用现有 FoodCandidate

不增加第二套录入结构。`FoodCandidate` 的 name/quantity/unit/expiryDate/gramsPerUnit/totalWeightGrams 原样保留。
name 标准化；quantity > 0，允许小数；无效 QDate 表示日期未知；重量 0 表示未知。
`addFoods(const QList<FoodCandidate>&, QString* error)` 继续整批事务保存，失败返回 false 且无部分入库。

- g、kg、斤分别按 1、1000、500 换算；现有 mg 兼容 0.001。
- 个/盒/袋等计数单位：总重量 = quantity × 用户填写的 gramsPerUnit。
- 未填单件重量则总重量未知；ml/L 不推测密度，不做默认鸡蛋/番茄重量表。
- B 重新计算总重量防止不一致，不能信任调用方随意传入的 totalWeightGrams。
- 修改原始数量必须同步重量；旧库迁移保持旧记录与未知值。

`InventoryBatch` 是 FoodCandidate 的只读标准 C++ 查询投影，加稳定 batchId，非新的录入来源。
B 查询不能合并掉批次。revision 为不透明库存版本，任何数量、日期、名称、重量变动均使其失效。
旧记录总重量为 0 时，质量单位可确定换算；计数单位仅在有合法 gramsPerUnit 时计算；其余仍未知。
转换后的已知总重量放入查询投影，原始数据迁移策略由 B 实现。已耗尽批次不得以未知重量继续参与匹配。

## B：统一评估与扣减

| 接口 | 责任 |
|---|---|
| getInventoryBatches | 读取所有批次和版本，报告读取错误 |
| evaluateRequirements | 对传入同一库存快照与日期纯评估，不写库存；D 一轮共用一份快照 |
| previewConsumption | 读最新库存并给出分配、状态、预览令牌，不执行扣减 |
| consumeForCooking | 验证令牌、重读库存，在 SQLite 事务内扣减并保存事件结果 |

需求 requiredGrams 必须 >0；同名合并。空需求、空名称、重复外部准备名或不在需求中的名称 InvalidArgument。
评估排除过期及 quantity<=0 的耗尽批次。knownAvailableGrams 仅累加可用已知重量。
knownGapGrams = max(requiredGrams-knownAvailableGrams,0)。状态规则：

1. 已知重量足够 => Enough（即便另有未知批次）。
2. 已知不足且另有可用未知批次 => Unknown。
3. 已知不足且没有未知批次 => Insufficient；不存在该食材也属于此项。

未知时的缺口只表示已知量差额，不得显示为确定补购量。
hasExpiringStock 表示存在可用、已知正重量的临期同名批次；仅供推荐“可利用”，不表示已经消耗。

FEFO：有到期日的按日期升序，同日按 batchId 升序，未知日期排最后并按 batchId 升序。
每批按自己的重量比例更新数量：quantityAfter = quantityBefore × weightAfter / weightBefore。
允许 4.5 个、0.6 袋，不四舍五入存储；无负库存。未知重量和过期批次永不自动扣减。

不足/未知且未逐项 externallyPreparedFoods 确认 => NeedsConfirmation/UnconfirmedIngredients，不写任何库存。
确认后只消耗可确认的库存量，其余按外部准备处理，不伪造入库；全部来自外部时也要保存零扣减事件。
令牌绑定规范化请求和库存版本。预览后库存变化 => NeedsConfirmation/InventoryChanged，重新预览确认。
B 在事务中检查版本；不允许先检查后在事务外修改造成竞态。
先检查事件是否已提交：同请求直接 AlreadyApplied，忽略旧令牌；不同请求 EventConflict。

扣减、事件请求和 ConsumptionResult 必须同事务提交。发生 SQL 错误整批回滚。
consumedExpiring 只能由实际 consumedGrams > 0 的临期批次决定。重试沿用原日期与原结果。

## C：查询、标签、饮食记录

实现 IRecipeService 五个方法，继续复用现有 Recipe、MealRecord、NutritionInfo。
getAllRecipes 提供完整菜谱，即使无库存；findRecipeById 返回完整菜谱；按日期查询与汇总报告文件读取错误。
公开查询不让 E/D 包含 src/recipe 内部仓库头文件。旧记录继续可读。
RecipeIngredient.amountGrams 是一份用量；营养按现有公式，不新增营养数据库。
菜谱时间包含准备/清洗/切配/烹饪/必要等待，必须为正整数；C 审核现有菜谱，不新增示例菜。

标签代码在 Tags 中统一。以下是本项目推荐标签规则，不是营养或医疗标准：

| 代码 | C 赋值标准，D 不能自行改义 |
|---|---|
| quick | 总时间 <=30 分钟 |
| easy | 现有步骤 <=5 且无需复杂技法，由 C 审核步骤 |
| light | 以蒸/煮/凉拌或少油清炒为主，无油炸/重油酱汁；人工审核 |
| appetizing | 酸香/鲜香等开胃风味，人工审核，不按热量推断 |
| hearty | 明确为丰盛主菜或有饱腹主食组合，人工审核 |
| special | 有特色做法/风味或节庆感，人工审核 |
| high_protein | C 现有公式算出一份蛋白质 >=20 g（内部筛选阈值，不作营养声称标准） |
| vegetable_rich | 一份非淀粉蔬菜重量 >=150 g，按配方人工核对，不把土豆/米面充数 |
| noodle | 以面条/粉类为主体的菜谱，排除米饭；不能只看“主食”分类 |

C 输出新的英文标签。旧中文标签只由 C 的适配器统一映射：快手→quick、简单→easy、清淡→light、开胃→appetizing、丰盛→hearty、特色→special、高蛋白→high_protein、蔬菜丰富→vegetable_rich、面食→noodle；映射后仍审核标准。
“家常/荤素”等旧标签可保留为附加信息，不当作上述标签的替代，不让 D/E 各写一份映射。

recordMealOnce 接收集成层冻结的 MealRecord（营养是本次总量），不根据后续变动菜谱重算。
record.recipeId >0、servings=1、date=time 前10字符；营养各项有限且非负。
相同 eventId + 相同 record 返回 AlreadyApplied 和 savedRecord；不同内容 EventConflict。
事件 ID 和记录用带版本格式一起保存；临时文件完整写入并可靠替换，失败保持原文件，旧无 eventId 记录仍读取。
损坏文件不得静默跳行后覆盖丢失记录；返回 InvalidData 供修复。无文件视为首次空库，权限错误返回 StorageFailure。

## E：奖励结果

applyCookingRewardOnce 只接受集成层调用，consumedExpiring 来自 B 已提交结果。
一次做饭 +10，实际消耗临期额外 +15（每事件一次），当日首次打卡 +5；新成就不额外加分。
同天两次做饭：做饭次数+2，打卡日只+1。保留现有连续打卡与成就。
奖励事件、积分依据、打卡日期一起持久化；失败不得只更新内存。继续使用原设置存储，保留旧记录。
相同事件返回原始结果，pointsAdded 不改成0；重放不新增奖励。totalPoints/totalCookingCount 是原始结算快照；UI 重读当前成长统计显示实时总数。
新解锁成就用稳定代码 `first_checkin` / `streak_3` / `streak_7`，中文显示由 E 映射。

## 集成层：完成与重试

由 A/组长维护独立协调服务，E 页面只调用 ICookingCompletionService。

1. previewCompletion：加载 C 菜谱与营养、规范化需求，调用 B 预览，返回冻结 snapshot 与 confirmationToken。
2. 用户确认后 completeCooking：验证令牌和请求；先在 SQLite 持久化 snapshot 与 Prepared 进度，再调用 B→C→E。
3. 每一步成功/AlreadyApplied 后记录进度；全部完成才返回 Succeeded、stage=Completed。
4. getPendingCompletions：返回已经持久化但未完成事件，含真实阶段和最后错误。
5. retryCompletion(eventId)：只读取已存快照，继续未完成步骤；不得重新取菜谱/时间或生成 UUID。

NotStarted 表示尚无持久化进度（例如令牌无效或首次保存失败）；Prepared 是已冻结尚未扣库存；InventorySaved、MealSaved、RewardSaved 是最后已持久化步骤。
字段 optional 仅在对应结果可用时赋值；部分成功仍返回 Failed 或 NeedsConfirmation，不能标全成功。
若模块成功而进度未记下就崩溃，重试模块靠持久化 eventId 返回 AlreadyApplied，再补记进度。
B 的扣减和 B 事件必须同事务；协调进度可以随后提交，靠幂等弥合窗口。

预览令牌不等于事件 ID。尚未 Prepared 时用户可修改外部准备清单重新预览；没有业务写入，取消无副作用。
Prepared 后请求和菜谱快照不可改变。B 尚未扣减但库存已变时，返回 NeedsConfirmation；同一请求重新预览仅刷新 B 分配/令牌，保留原菜谱/时间快照，用户确认后 completeCooking 继续。
如果要改冻结请求，拒绝 EventConflict；不要静默复用 ID 改清单。
B 已成功后不再重新预览扣减。retryCompletion 必须在 B 幂等查验之前避免因旧令牌失效而拒绝已完成事件。

幂等比较使用规范化字段内容，不用显示文本/内存地址/std::hash 或仅时间戳：排序合并需求、排序外部准备清单、比较全部业务字段；令牌不属于事件内容。
协调层保存 recipe、营养、请求；B 保存需求/时间/外部准备；C 保存 MealRecord；E 保存时间/临期标记。
同事件冲突不能自动换 UUID 重试。一次新的实际做饭才能创建新事件。
