## 统一基础规则

| 项目 | 确定约定 |
|---|---|
| 食材匹配 | A 的标准名称，C 同步名称；同名需求先合并，不另发明 foodId |
| 批次 ID | B 数据库稳定正数 `int64_t`，不能是列表下标 |
| 菜谱 ID | 现有正数 `int`；找不到返回 Failed/NotFound |
| 份数 | 本版只接受 1；其他值 InvalidArgument，预留字段供未来扩展 |
| 计算重量 | 克；所有数量/重量要求有限数值，拒绝 NaN/Inf/负数 |
| 日期 | YYYY-MM-DD；仅到期日允许空字符串表示未知 |
| 完成时间 | YYYY-MM-DD HH:mm:ss，应用时区 Asia/Shanghai，重试不重新取今天 |
| 临期 | 完成事件当天到未来 3 天，含两端；过期是到期日严格早于当天 |
| 事件编号 | 集成层生成小写、无花括号 UUID；每次实际做饭一次，重试沿用 |
| 浮点误差 | 计算不按 UI 小数位舍入；比较容差 1e-6 g，仅容差内尾差可归零 |

`OperationResult`：Succeeded=本次成功；AlreadyApplied=同一事件已保存；NeedsConfirmation=本次尚未执行需确认的步骤（已有成功阶段不会回滚），需重新确认；Failed=失败。
成功/已处理的 errorCode 为 None，失败/需确认必须提供对应错误码和中文 message。
查询只返回 Succeeded 或 Failed；Succeeded + 空列表表示确实无数据，不能把读取失败伪装为空库存。
InvalidState 用于当前阶段不允许的操作（如扣减后取消）；NotFound 用于不存在的菜谱/事件；InvalidData 用于已损坏的存储内容；EventConflict 表示同 ID 不同内容。
幂等返回携带原始保存结果，界面不能再次把 pointsAdded 加到自己的累计值。

## A/B：沿用现有 FoodCandidate

不增加第二套录入结构。`FoodCandidate` 的 name/quantity/unit/expiryDate/gramsPerUnit/totalWeightGrams 原样保留。
name 标准化；quantity > 0，允许小数；无效 QDate 表示日期未知；重量 0 表示未知。
`addFoods(const QList<FoodCandidate>&, QString* error)` 继续整批事务保存，失败返回 false 且无部分入库。

- g、kg、斤分别按 1、1000、500 换算；现有 mg 兼容 0.001。
- 个/盒/袋等计数单位：总重量 = quantity × 用户填写的 gramsPerUnit。
- 未填单件重量则总重量未知；ml/L 不推测密度，不做默认鸡蛋/番茄重量表。
- B 重新计算总重量防止不一致，不能信任调用方随意传入的 totalWeightGrams。
- 修改原始数量必须同步重量；旧库迁移保持旧记录与未知值。

`InventoryBatch` 是 FoodCandidate 的只读标准 C++ 查询投影，加稳定 batchId，非新的录入来源。
B 查询不能合并掉批次。revision 为不透明库存版本，任何数量、日期、名称、重量变动均使其失效。
旧记录总重量为 0 时，质量单位可确定换算；计数单位仅在有合法 gramsPerUnit 时计算；其余仍未知。
转换后的已知总重量放入查询投影，原始数据迁移策略由 B 实现。已耗尽批次不得以未知重量继续参与匹配。

## B：统一评估与扣减

| 接口 | 责任 |
|---|---|
| getInventoryBatches | 读取所有批次和版本，报告读取错误 |
| evaluateRequirements | 对传入同一库存快照与日期纯评估，不写库存；D 一轮共用一份快照 |
| getConsumption | 按 eventId 查询已提交扣减结果；不存在返回 Failed/NotFound，读失败明确返回 StorageFailure |
| previewConsumption | 读最新库存并给出分配、状态、预览令牌，不执行扣减 |
| consumeForCooking | 验证令牌、重读库存，在 SQLite 事务内扣减并保存事件结果 |

需求 requiredGrams 必须 >0；同名合并。空需求、空名称、重复外部准备名或不在需求中的名称 InvalidArgument。
评估排除过期及 quantity<=0 的耗尽批次。knownAvailableGrams 仅累加可用已知重量。
knownGapGrams = max(requiredGrams-knownAvailableGrams,0)。状态规则：

1. 已知重量足够 => Enough（即便另有未知批次）。
2. 已知不足且另有可用未知批次 => Unknown。
3. 已知不足且没有未知批次 => Insufficient；不存在该食材也属于此项。

未知时的缺口只表示已知量差额，不得显示为确定补购量。
hasExpiringStock 表示存在可用、已知正重量的临期同名批次；仅供推荐“可利用”，不表示已经消耗。

FEFO：有到期日的按日期升序，同日按 batchId 升序，未知日期排最后并按 batchId 升序。
每批按自己的重量比例更新数量：quantityAfter = quantityBefore × weightAfter / weightBefore。
允许 4.5 个、0.6 袋，不四舍五入存储；无负库存。未知重量和过期批次永不自动扣减。

不足/未知且未逐项 externallyPreparedFoods 确认 => NeedsConfirmation/UnconfirmedIngredients，不写任何库存。
确认后只消耗可确认的库存量，其余按外部准备处理，不伪造入库；全部来自外部时也要保存零扣减事件。
令牌绑定规范化请求和库存版本。预览后库存变化 => NeedsConfirmation/InventoryChanged，重新预览确认。
B 在事务中检查版本；不允许先检查后在事务外修改造成竞态。
先检查事件是否已提交：同请求直接 AlreadyApplied，忽略旧令牌；不同请求 EventConflict。

扣减、事件请求和 ConsumptionResult 必须同事务提交。发生 SQL 错误整批回滚。
consumedExpiring 只能由实际 consumedGrams > 0 的临期批次决定。重试沿用原日期与原结果。

## C：查询、标签、饮食记录

实现 IRecipeService 五个方法，继续复用现有 Recipe、MealRecord、NutritionInfo。
getAllRecipes 提供完整菜谱，即使无库存；findRecipeById 返回完整菜谱；按日期查询与汇总报告文件读取错误。
公开查询不让 E/D 包含 src/recipe 内部仓库头文件。旧记录继续可读。
RecipeIngredient.amountGrams 是一份配方用量（不声称严格等于一个人的食量）；营养按现有公式，不新增营养数据库。
所有 ingredients 中的正重量项均属必要食材，包含食用油、姜蒜等；不在列表里的盐/糖等不凭空加入。D 与扣减使用完全相同的需求集合，不暗设“调料免费”。未知密度的油/可乐需录入实测重量或由用户确认另行准备。
菜谱时间包含准备/清洗/切配/烹饪/必要等待，必须为正整数；C 审核现有菜谱，不新增示例菜。

标签代码在 Tags 中统一。以下是本项目推荐标签规则，不是营养或医疗标准：

| 代码 | C 赋值标准，D 不能自行改义 |
|---|---|
| quick | 总时间 <=30 分钟 |
| easy | 现有步骤 <=5 且无需复杂技法，由 C 审核步骤 |
| light | 以蒸/煮/凉拌或少油清炒为主，无油炸/重油酱汁；人工审核 |
| appetizing | 酸香/鲜香等开胃风味，人工审核，不按热量推断 |
| hearty | 明确为丰盛主菜或有饱腹主食组合，人工审核 |
| special | 有特色做法/风味或节庆感，人工审核 |
| high_protein | C 现有公式算出一份蛋白质 >=20 g（内部筛选阈值，不作营养声称标准） |
| vegetable_rich | 一份非淀粉蔬菜重量 >=150 g，按配方人工核对，不把土豆/米面充数 |
| noodle | 以面条/粉类为主体的菜谱，排除米饭；不能只看“主食”分类 |

C 输出新的英文标签。旧中文标签只由 C 的适配器统一映射：快手→quick、简单→easy、清淡→light、开胃→appetizing、丰盛→hearty、特色→special、高蛋白→high_protein、蔬菜丰富→vegetable_rich、面食→noodle；映射后仍审核标准。
“家常/荤素”等旧标签可保留为附加信息，不当作上述标签的替代，不让 D/E 各写一份映射。

recordMealOnce 接收集成层冻结的 MealRecord（营养是本次总量），不根据后续变动菜谱重算。
record.recipeId >0、servings=1、date=time 前10字符；营养各项有限且非负。
相同 eventId + 相同 record 返回 AlreadyApplied 和 savedRecord；不同内容 EventConflict。
事件 ID 和记录用带版本格式一起保存；临时文件完整写入并可靠替换，失败保持原文件，旧无 eventId 记录仍读取。
损坏文件不得静默跳行后覆盖丢失记录；返回 InvalidData 供修复。无文件视为首次空库，权限错误返回 StorageFailure。

## D/E：复用推荐结构

旧 UserContext 新增 `optional<RecommendationPreferences> preferences` 和 `inventorySnapshot`；新服务必须要求 preferences 存在。
新路径以 preferences 为唯一条件，以 inventorySnapshot 为唯一库存来源，忽略旧 mood/maxPreparationMinutes/topK/servings/inventory/expiringIngredients，避免两个来源冲突。
原 excludedIngredients 仍是硬排除；原 targetCaloriesPerServing >0 时可沿用现有能量评分，0 禁用。
旧自由函数仍保留原语义；E 接入新服务后不能混用。旧枚举数字与新五心情无转换关系，不可 static_cast。
Recommendation 原字段不删除：recipeId/recipe/servings/nutrition/分数等继续填写；新增 role、availability、reasons。
新卡片 dishName=recipe.name、recipeId=recipe.id、servings=1、effectiveMaxPreparationMinutes=最终上限；旧 mood 字段在新路径不用于 UI 判断。
已有 availableIngredients/missingIngredients 可做摘要，但未知状态必须以 availability 为准，不得丢掉未知。
reasons 1～2 条；总分及各分项沿用 0～100 量纲，权重由 D 维护，不作为跨模块协议。

| 五种心情 | 默认时间 | 主要方向 | 三个按钮 |
|---|---:|---|---|
| Tired 很累 | 30 | quick/easy/少缺口 | Simpler、NoNoodles、OnlyInventory |
| WantGoodFood 想吃点好的 | 45 | hearty/appetizing | Heartier、Lighter、OnlyInventory |
| LowAppetite 没胃口 | 30 | appetizing/light | MoreAppetizing、Lighter、Simpler |
| WantLight 想清爽一点 | 40 | light/vegetable_rich | MoreVegetables、MoreProtein、Simpler |
| TreatMyself 想犒劳自己 | 75 | hearty/special | MoreSpecial、SmallPurchase、时间短一点 |

E 选心情填默认时间，之后用户上限为最终硬限制，不能再取 mood 默认值和用户值的最小值。
未选心情/上限<=0/份数非1 => Failed/InvalidArgument。
refinement 同时只保留一个，再次点击取消；库存模式和时间单独保留。
“时间短一点”设置 maxPreparationMinutes=min(当前值,45)，当前<=45不增大；E 提示当前已经在45分钟内。
切心情恢复默认、清空偏好和排除记录；修改时间/偏好/库存模式/库存版本清空 excludedRecipeIds。

库存模式：PreferInventory 可补购；OnlyInventory 所有必要食材 Enough；SmallPurchase 最多2种 Insufficient 且不能有 Unknown。
NoNoodles 是硬排除，其余 refinement 是排序偏好，不擅自突破时间或库存约束。
新服务从 C 全量菜谱出发、用 B 评估同一快照；不再把旧 findRecipesByFoods 当全量候选入口。
先选 Primary，再从剩余选 AlternativeOne（更突出快捷/清淡等侧重点）、AlternativeTwo（主要食材/做法/类别不同）。不足3张仅返回实际数量。
卡片顺序与 role 对齐且 recipeId 去重；换批排除此前全部展示 ID，稳定同分按 ID 升序；hasMore 表示还有未展示的合格菜谱。
无结果是 Succeeded+空 cards，并给可读提示；失败是 Failed，E 区分展示。
推荐只读，不扣库存、记饮食、发奖励。详情与完成预览重新评估最新库存。

## E：奖励结果

applyCookingRewardOnce 只接受集成层调用，consumedExpiring 来自 B 已提交结果。
一次做饭 +10，实际消耗临期额外 +15（每事件一次），当日首次打卡 +5；新成就不额外加分。
同天两次做饭：做饭次数+2，打卡日只+1。保留现有连续打卡与成就。
奖励事件、积分依据、打卡日期一起持久化；失败不得只更新内存。继续使用原设置存储，保留旧记录。
相同事件返回原始结果，pointsAdded 不改成0；重放不新增奖励。totalPoints/totalCookingCount 是原始结算快照；UI 重读当前成长统计显示实时总数。
新解锁成就用稳定代码 `first_checkin` / `streak_3` / `streak_7`，中文显示由 E 映射。
跨天重试按 completedAt 日期记账，不把今日奖励挪到重试日期。
getGrowthSnapshot(referenceDate) 返回当前持久化状态，不返回某个历史事件的总分。总次数/总分统计全部已保存记录，日期只影响当天打卡标记与当前连续天数（从参考日或其前一天往前数）；recentCheckInDates 是最近7个打卡日期倒序。
现有 checkIn() 与新奖励服务必须共享同一个 RewardSystem 和可靠写入路径。手动打卡后做饭不再加每日5分；反向亦然。旧打卡日期贡献5分但不虚构历史做饭次数。changed() 在成功持久化后发出；失败不更新UI累计值。

## 集成层：完成与重试

由 A/组长维护独立协调服务，E 页面只调用 ICookingCompletionService。

1. previewCompletion：加载 C 菜谱与营养、规范化需求，调用 B 预览，返回冻结 snapshot 与 confirmationToken。
2. 用户确认后 completeCooking：验证令牌和请求；先在 SQLite 持久化 snapshot 与 Prepared 进度，再调用 B→C→E。
3. 每一步成功/AlreadyApplied 后记录进度；全部完成才返回 Succeeded、stage=Completed。
4. getPendingCompletions：返回已经持久化但未完成事件，含真实阶段和最后错误。
5. retryCompletion(eventId)：只读取已存快照，继续未完成步骤；不得重新取菜谱/时间或生成 UUID。
6. getCompletion(eventId)：返回冻结 snapshot 和 progress；E 重启后可恢复原请求、详情与外部准备清单，再进行预览或取消。
7. cancelPreparedCompletion(eventId)：仅在 B 确认尚未提交扣减时允许取消，持久化 Cancelled 状态；不补偿或撤销已成功扣减。

NotStarted 表示尚无持久化进度（例如令牌无效或首次保存失败）；Prepared 是已冻结尚未扣库存；InventorySaved、MealSaved、RewardSaved 是最后已持久化步骤。
字段 optional 仅在对应结果可用时赋值；部分成功仍返回 Failed 或 NeedsConfirmation，不能标全成功。
若模块成功而进度未记下就崩溃，重试模块靠持久化 eventId 返回 AlreadyApplied，再补记进度。
B 的扣减和 B 事件必须同事务；协调进度可以随后提交，靠幂等弥合窗口。

预览令牌不等于事件 ID。尚未 Prepared 时用户可修改外部准备清单重新预览；没有业务写入，取消无副作用。
Prepared 后请求和菜谱快照不可改变。B 尚未扣减但库存已变时，返回 NeedsConfirmation；同一请求重新预览仅刷新 B 分配/令牌，保留原菜谱/时间快照，用户确认后 completeCooking 继续。
如果要改冻结请求，拒绝 EventConflict；不要静默复用 ID 改清单。
若库存变化使原外部准备清单不再适用，E 提供“取消本次待处理记录后重新确认”：协调层串行锁住事件，调用 B.getConsumption。只有明确 NotFound 才可写 Cancelled；读失败或已有扣减均不可取消。取消保留 tombstone，不删除记录；重复取消返回 AlreadyApplied+Cancelled。取消后用户明确重新确认可为这次尚未结算的做饭创建新 UUID，禁止对已扣减事件这样处理。
getPendingCompletions 排除 Completed 和 Cancelled；retry/complete 对 Cancelled 返回 Failed/InvalidState。未持久化过的预览直接丢弃，不调用取消接口。
B 已成功后不再重新预览扣减。retryCompletion 先调用 B.getConsumption，已存在时核对原请求（B 内部保存原请求，consumeForCooking 同请求重放仍须核对），补齐阶段；读失败立即停止，不能当作尚未扣减。
为避免 getConsumption 只返回结果无法核对内容，恢复时仍调用 consumeForCooking(持久化的原请求, 原令牌)：它必须先核对已保存请求并返回 AlreadyApplied，再考虑令牌。原请求和令牌由协调日志保存。
B 尚未提交且重启导致令牌丢失时，retry 返回 NeedsConfirmation/InventoryChanged；E 用 getCompletion 的原请求重新预览、明确确认。不得在后台生成新令牌并当用户已同意。
previewConsumption 未确认不足项时返回 NeedsConfirmation+availability+planned，previewToken 为空；确认清单齐全且预览成功才返回非空令牌。previewCompletion 同理透传可展示明细；无成功令牌不能开始 Prepared 保存。

幂等比较使用规范化字段内容，不用显示文本/内存地址/std::hash 或仅时间戳：排序合并需求、排序外部准备清单、比较全部业务字段；令牌不属于事件内容。
协调层保存 recipe、营养、请求；B 保存需求/时间/外部准备；C 保存 MealRecord；E 保存时间/临期标记。
同事件冲突不能自动换 UUID 重试。只有一次新的实际做饭，或明确取消尚未扣减事件后重新确认，才能创建新事件。

## 存储与兼容的实施细则

- B 数据源仍为现有 shixu.db 和同一 InventoryManager。适配器在 B 内部访问其连接/私有方法，不能从 getAllItems() 伪造 batchId；constructor/destructor 仍由主窗口管理，适配器不得关闭连接。
- B 为库存版本与扣减事件建表；addFoods、所有后续写入与版本更新同事务。查询在同一读事务取得批次及版本。耗尽批次 quantity=0、totalWeightGrams=0，旧库存/首页/临期查询也排除耗尽批次，避免显示“0个库存”。
- B 查询投影不把非法日期或损坏数字静默改成未知；失败返回 InvalidData。合法未知为NULL/空日期，已知总重>0优先；新写入仍重新计算。原始存储单位、数量不改成纯克。
- 名称匹配只对已经标准化的名称精确比较，当前A字典覆盖西红柿→番茄、马铃薯/洋芋→土豆。C 内置配方保持同一标准名。不自动把“猪肉”和“猪里脊”视为同一食材，不补重量估算。旧非标准名称的修复由A/组长统一迁移，不让B/D复制别名表。
- C 的新服务使用传入 mealRecordsPath（默认组装时传现有 meal_records.txt）；旧 recordMeal 必须走同一文件配置，不能各开一套。UTF-8文件路径在Windows用 std::filesystem::u8path 转换。
- C 保留旧读取方法兼容已有测试，新接口增加严格读取。新写入前完整校验旧内容；未知版本/损坏数据不覆盖。保持旧管道格式可读，新格式自行版本化，但名称中的管道/换行须转义或长度编码。double 按 max_digits10 精度保存，避免重启后相同事件被误判为冲突。
- C 原 append 新增可靠路径时必须保留新格式事件；不能通过旧API写入而丢掉去重信息。文件替换不得先删除原文件；Windows用可覆盖目标的原子替换机制，失败保留旧文件。
- E 原 rewards.ini 路径和 checkIn/dates 保留；统一写入完整状态并检查sync结果，严禁“事件已记、积分未记”的分离提交。若实现无法保证多个设置键原子性，将新事件及奖励状态序列化为一个版本化状态载荷，并在同一次可靠替换中保存。
- 集成日志固定为 shixu.db 同目录的 cooking_events.sqlite；只存快照/阶段/令牌/错误/取消标记，不复制库存表。此连接属于协调日志，B仍只使用原库存连接。三个业务服务在同一进程由一个协调器串行调用，本版不承诺多进程并发运行。
- enum 必须校验有效值；日期须为真实日历日期，不仅判断字符串长度。每次新操作的 referenceDate/completedAt 由集成层按应用时区生成；测试显式传固定日期。
- 快照和请求在持久化前规范化，排序合并后用相同序列化结果比对；double 不用显示小数位，也不用带容差的比较来允许更改事件内容。令牌是进程内预览标识，不做跨进程安全认证；失效时要求重确认。
